# Базовые аутбаунды и группы балансировки

В этом разделе описаны базовые системные аутбаунды (`direct`, `block`, `dns`), классические прокси-клиенты (`socks`, `http`), группы выбора и балансировки (`selector`, `urltest`), многошаговые цепочки (`chain`) и мостовой аутбаунд (`bridge`).

Общие параметры подключения (`dialer`), TLS и UoT описаны в [Общих объектах конфигурации](../common-objects.md).

---

## `direct`

Отправляет TCP-соединения и UDP-дейтаграммы напрямую к целевому узлу без промежуточного прокси.

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"direct"`. |
| `tag` | `string` | `""` | Уникальный тег аутбаунда. |
| `override_address` | `string` | `""` | **Устарело и удалено.** Любое непустое значение отклоняется валидатором; используйте `route-options` в правилах маршрутизации. |
| `override_port` | `integer` | `0` | **Устарело и удалено.** Любое ненулевое значение отклоняется валидатором; используйте `route-options`. |
| `proxy_protocol` | `integer` | `0` | **Устарело и удалено.** Любое ненулевое значение отклоняется валидатором. |
| *Поля `dialer`* | — | — | Все поля диалера из [Общих объектов](../common-objects.md), **за исключением `detour`**. |

### Ограничения и особенности

- Использование `detour` в `direct` запрещено и отклоняется при проверке конфигурации.
- Поддерживает TCP и UDP, а также системное разрешение доменов через `domain_resolver` / `domain_strategy`.

### Пример

```json
{
  "type": "direct",
  "tag": "direct",
  "routing_mark": 255,
  "connect_timeout": "5s"
}
```

## `block`

Немедленно отклоняет все направленные на него TCP- и UDP-подключения (ошибка `ConnectionRefused`).

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"block"`. |
| `tag` | `string` | `""` | Уникальный тег аутбаунда. |

Дополнительные поля (включая поля `dialer`) не допускаются.

### Пример

```json
{
  "type": "block",
  "tag": "block"
}
```

## `dns`

**Устарел и удалён в `tachyon-core`.**

Наличие объекта `{"type": "dns", ...}` в массиве `outbounds` приводит к ошибке валидации конфигурации. Для перехвата DNS-запросов используйте действие маршрутизации `"action": "hijack-dns"` в `route.rules` (см. [Маршрутизация и наборы правил](../route-and-rulesets.md)).

## `socks`

Клиент протоколов SOCKS4, SOCKS4a и SOCKS5. Поддерживает TCP-подключения, UDP-ретрансляцию через `UDP ASSOCIATE` (только SOCKS5) и инкапсуляцию UDP поверх TCP (`udp_over_tcp`).

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"socks"`. |
| `tag` | `string` | `""` | Уникальный тег аутбаунда. |
| `server` | `string` | — | Обязательно: IP-адрес или доменное имя SOCKS-сервера. |
| `server_port` | `integer` | — | Обязательно: порт сервера (`1..=65535`). |
| `version` | `string` | `"5"` | Версия протокола: `"4"`, `"4a"` или `"5"`. В runtime `"4"` автоматически использует расширение 4a при невозможности локального IPv4-разрешения домена. |
| `username` | `string` | `""` | Логин аутентификации (для SOCKS5 `0x02`, используется совместно с `password`). |
| `password` | `string` | `""` | Пароль аутентификации (максимум 255 байт на каждое поле). |
| `network` | `string` \| `string[]` | `["tcp", "udp"]` | Ограничение по транспортному протоколу: `"tcp"`, `"udp"` или оба. |
| `udp_over_tcp` | `boolean` \| `object` | `false` | Включает передачу UDP поверх TCP (UoT v1/v2). Подробнее см. в [Общих объектах](../common-objects.md). |
| *Поля `dialer`* | — | — | Стандартные поля диалера. |

### Особенности поведения

- В режиме SOCKS4/4a поддерживается только TCP; попытка UDP-подключения возвращает ошибку, если не включён `udp_over_tcp`.
- Для SOCKS5 UDP ASSOCIATE поддерживаются адреса IPv4, IPv6 и доменные имена (RFC 1928); управляющее TCP-соединение удерживается открытым на время жизни UDP-сессии.
- Объект `tls` для `socks` не поддерживается.

### Пример

```json
{
  "type": "socks",
  "tag": "socks-out",
  "server": "127.0.0.1",
  "server_port": 1080,
  "version": "5",
  "username": "user",
  "password": "secret",
  "udp_over_tcp": {
    "enabled": true,
    "version": 2
  }
}
```

## `http`

Клиент HTTP/1.1 `CONNECT`-прокси. Поддерживает только TCP; при необходимости защищается внешним слоем TLS (HTTPS-прокси).

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"http"`. |
| `tag` | `string` | `""` | Уникальный тег аутбаунда. |
| `server` | `string` | — | Обязательно: адрес прокси-сервера. |
| `server_port` | `integer` | — | Обязательно: порт прокси-сервера (`1..=65535`). |
| `username` | `string` | `""` | Логин для заголовка `Proxy-Authorization: Basic` (задаётся совместно с `password`). |
| `password` | `string` | `""` | Пароль для заголовка `Proxy-Authorization: Basic`. |
| `path` | `string` | `""` | Опциональный путь (принимается валидатором для совместимости схемы). |
| `headers` | `object` | `{}` | Дополнительные HTTP-заголовки (`map[string]string` или `map[string]string[]`). |
| `tls` | `object` | — | Опциональный клиентский объект TLS (см. [Общие объекты](../common-objects.md)). |
| *Поля `dialer`* | — | — | Стандартные поля диалера. |

### Особенности поведения

- Корректно пропускает промежуточные ответы `1xx` (например, `100 Continue`) и сохраняет данные протоколов, в которых сервер начинает передачу первым (например, SSH-баннер), даже если они пришли в одном TCP-сегменте с заголовком `200 OK`.
- UDP не поддерживается.

### Пример

```json
{
  "type": "http",
  "tag": "https-proxy",
  "server": "proxy.example.com",
  "server_port": 8443,
  "username": "client",
  "password": "password123",
  "tls": {
    "enabled": true,
    "server_name": "proxy.example.com"
  }
}
```

## `selector`

Группа ручного выбора одного активного исходящего тега из заданного списка. Активный элемент можно переключать в реальном времени через Clash API (`PUT /proxies/{name}`), а выбор сохраняется между перезапусками при включённом `experimental.cache_file`.

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"selector"`. |
| `tag` | `string` | — | Уникальный тег группы. |
| `outbounds` | `string[]` | — | Обязательно: непустой список тегов участников (других `outbounds` или `endpoints`). |
| `default` | `string` | `outbounds[0]` | Тег участника, выбранного по умолчанию при первом запуске. Должен входить в `outbounds`. |
| `interrupt_exist_connections` | `boolean` | `false` | Если `true`, при ручном переключении активного участника существующие соединения через предыдущий тег принудительно закрываются. |
| `auto_failover` | `boolean` | `false` | Если `true`, при отказе активного участника по результатам проверки `selector` автоматически переключается на доступного резервного участника из `outbounds`. По умолчанию `false` — группа остаётся на выбранном пользователем узле. |

### Пример

```json
{
  "type": "selector",
  "tag": "proxy",
  "outbounds": ["auto", "eu-vless", "us-hy2", "direct"],
  "default": "auto",
  "interrupt_exist_connections": true,
  "auto_failover": false
}
```

## `urltest`

Группа автоматического тестирования и балансировки исходящих подключений. Поддерживает 12 режимов работы: от классического выбора узла с минимальной задержкой до взвешенного распределения, консистентного хеширования потоков, многоуровневых приоритетов, хеджирования запросов, учёта пропускной способности и квот трафика.

### Основные поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"urltest"`. |
| `tag` | `string` | — | Уникальный тег группы. |
| `outbounds` | `string[]` | — | Обязательно: непустой список тегов участников. Допускается вложенность других `urltest` и `selector`. |
| `url` | `string` | `"https://www.gstatic.com/generate_204"` | HTTP/HTTPS URL для активных проверок доступности и RTT. |
| `interval` | `duration` | `"3m"` (`180s`) | Интервал фоновых проверок участников. На холодном старте при отсутствии живых измерений интервал временно сокращается до `min(interval, 15s)` для быстрого прогрева. |
| `tolerance` | `integer` | `50` | Порог гистерезиса в миллисекундах (`0..=65535`): новый узел становится активным, только если его задержка (или композитная метрика в `stability`) лучше текущего более чем на `tolerance` мс. |
| `idle_timeout` | `duration` | — | Длительность простоя (принимается валидатором для совместимости схемы). |
| `interrupt_exist_connections` | `boolean` | `false` | Если `true`, при переключении с недоступного или помещённого в карантин участника существующие соединения на старом теге закрываются. |
| `mode` | `string` | `"least_test"` | Режим выбора и балансировки (см. таблицу ниже). |
| `balancer` | `object` | — | Дополнительные настройки пула, уровней приоритета, хеширования и квот (см. ниже). |

### Все поддерживаемые режимы (`mode`)

| Режим (`mode`) | Допустим `balancer` | Алгоритм выбора и поведение |
|---|---|---|
| `least_test` *(или `""`)* | Нет | Режим по умолчанию. Параллельно измеряет HTTP RTT всех участников и выбирает узел с минимальной задержкой с учётом гистерезиса `tolerance`. При активных соединениях на текущем узле сглаживает скачки RTT через EWMA. |
| `failover` | Нет | При первом запуске измеряет всех участников и закрепляет самый быстрый. Далее проверяет **только** активного участника раз в `interval`. Переключение на следующий узел происходит исключительно при отказе текущего. |
| `round_robin` | Да | Циклически распределяет новые соединения по активному пулу кандидатов (`balancer.pool`, `balancer.pool_tolerance`). Если задан непустой `balancer.sticky_hash` (кроме `["none"]`), автоматически использует консистентное хеширование. |
| `stability` | Да | Выбирает один наиболее стабильный узел по композитной оценке, учитывающей текущий RTT, сглаженный EWMA RTT, джиттер (RFC 3550) и накопленный штраф за потери/таймауты, с гистерезисом `tolerance`. |
| `sticky` | Да | Консистентное распределение потоков (Rendezvous / HRW-хеширование) по пулу кандидатов на основе ключей `balancer.sticky_hash`. По умолчанию привязывает поток к кортежу `["source_ip", "domain", "dest_ip"]`, группируя поддомены по регистрируемому домену (`eTLD+1`) и IPv6-клиентов по префиксу `/64`. |
| `least_load` | Да | Направляет каждое новое соединение на узел из пула кандидатов с минимальной оценкой нагрузки `(active_conns + 1) * RTT`, выравнивая число одновременных потоков с учётом задержки. |
| `weighted` | Да | Плавный взвешенный Round-Robin (Smooth Weighted Round-Robin, SWRR) внутри пула кандидатов: вес каждого узла обратно пропорционален квадрату его задержки (`(best_rtt / rtt)^2`), благодаря чему более быстрые серверы получают большую долю трафика. |
| `passive` | Да | Учитывает пассивную телеметрию реальных соединений: время до первого байта ответа, отказы подключения и зависания без входящих данных (`zero-RX stall`), без необходимости полагаться исключительно на активные пробы. |
| `priority` | Да | Строгий приоритет по порядку в списке `outbounds` (или по уровням `balancer.tiers`): выбирает **первого** доступного участника в списке с приемлемой стабильностью, автоматически возвращаясь к нему после восстановления. |
| `hedged` | Да | Хеджирование TCP-соединений для снижения хвостовых задержек: начинает подключение через основного кандидата и, если задержка установки превышает адаптивный порог (`1.5 * EWMA RTT`, в пределах `80..600` мс), запускает параллельную попытку через резервного кандидата и использует первое успешное соединение. |
| `throughput` | Да | Оценивает фактическую скорость передачи на живых потоках (EWMA KiB/s) и выбирает узел с лучшим соотношением стабильности и наблюдаемой пропускной способности, штрафуя сильно ограниченные по скорости каналы (`< 32 KiB/s`). |
| `quota` | Да | Распределяет трафик с учётом накопленного объёма переданных данных и лимита `balancer.quota_mib`: предпочитает узлы, не исчерпавшие квоту, балансируя нагрузку с учётом уже переданного объёма и стабильности. |

Во всех режимах при ошибке подключения (TCP или UDP) группа выполняет автоматический перебор до 8 резервных участников в рамках одного вызова, а пассивный предохранитель (circuit breaker) временно переводит в карантин узлы с повторяющимися отказами или ранними обрывами (`< 64 KiB`) на разных целевых хостах, чтобы сбой одного внешнего сайта не выводил из строя исправный прокси.

### Поля объекта `balancer`

Объект `balancer` допускается для всех режимов, кроме `least_test` (и пустого `mode`) и `failover`. Пустой объект `{}` игнорируется.

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `pool` | `integer` | `0` (без ограничения, до 64) | Максимальное число лучших кандидатов, включаемых в рабочий пул балансировки. Валидатор требует неотрицательное целое (`>= 1` для ограничения). |
| `pool_tolerance` | `integer` | `max(tolerance, 150)` | Максимально допустимое отклонение задержки кандидата (в миллисекундах) от лучшего узла для попадания в пул. Диапазон: `0..=15000`. |
| `sticky_hash` | `string[]` | `["source_ip", "domain", "dest_ip"]` (для `sticky`) | Компоненты ключа привязки потока: `"source_ip"`, `"domain"`, `"dest_ip"`, `"dest_port"`, `"process"`. Значение `["none"]` отключает привязку и не может комбинироваться с другими компонентами. |
| `quota_mib` | `integer` | `0` | Целевой порог переданного трафика на одного участника в МиБ (используется в режиме `quota`; `0` — равномерное выравнивание объёма без жёсткого потолка). |
| `tiers` | `string[][]` | `[]` | Многоуровневые группы приоритета: массив массивов тегов из `outbounds`. Пока в более высоком уровне есть хотя бы один здоровый участник, выбор и балансировка ограничены этим уровнем; переход на следующий уровень происходит только при деградации всех узлов предыдущего. |

### Примеры

Балансировка по пулу с привязкой сессий (`sticky`):

```json
{
  "type": "urltest",
  "tag": "auto-sticky",
  "outbounds": ["nl-1", "de-1", "fi-1", "se-1"],
  "url": "https://www.gstatic.com/generate_204",
  "interval": "3m",
  "tolerance": 50,
  "mode": "sticky",
  "balancer": {
    "pool": 3,
    "pool_tolerance": 120,
    "sticky_hash": ["source_ip", "domain"]
  }
}
```

Приоритетное резервирование по уровням (`priority` + `tiers`):

```json
{
  "type": "urltest",
  "tag": "tiered-failover",
  "outbounds": ["primary-1", "primary-2", "backup-1", "backup-2"],
  "mode": "priority",
  "interval": "1m",
  "interrupt_exist_connections": true,
  "balancer": {
    "tiers": [
      ["primary-1", "primary-2"],
      ["backup-1", "backup-2"]
    ]
  }
}
```

## `chain`

Организует последовательную многошаговую цепочку исходящих подключений: трафик проходит от первого элемента к последнему (`outbounds[0]` -> `outbounds[1]` -> ... -> `outbounds[N-1]` -> целевой адрес), не требуя дублирования конфигураций с жёстко прописанным полем `detour`.

### Поддерживаемые поля

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"chain"`. |
| `tag` | `string` | `"chain"` | Уникальный тег цепочки. |
| `outbounds` | `string[]` | — | Обязательно: не менее 2 тегов участников в порядке от входного звена к выходному. |
| `idle_timeout` | `duration` | — | Таймаут простоя (принимается валидатором для совместимости схемы). |
| `strip_evasion` | `boolean` | `false` | Упрощённый флаг снятия избыточной маскировки на внутренних звеньях цепочки (например, ограничивает длину padding в XHTTP-звеньях нижним пределом). |
| `strip` | `object` | `{}` | Точечное управление снятием параметров на внутренних звеньях (`map[string]bool`). Допустимые ключи: `"multiplex.padding"`, `"tls.fragment"`, `"tls.utls"`, `"xhttp.padding"`. |
| `rewrite` | `object` | `{}` | Правила перезаписи параметров звеньев (принимается валидатором для совместимости схемы). |
| `interrupt_exist_connections` | `boolean` | `false` | Закрывать активные соединения при переключении участников внутри цепочки. |

### Особенности поведения

- Последний элемент `outbounds` выступает выходным узлом (подключается к целевому адресу), а все предыдущие формируют стек промежуточных `detour`-звеньев.
- Поддерживает как TCP, так и UDP (при условии, что выходной и промежуточные узлы поддерживают соответствующий транспорт).
- Ключи в `strip` переопределяют общее значение `strip_evasion` для соответствующего параметра.

### Пример

```json
{
  "type": "chain",
  "tag": "double-hop",
  "outbounds": ["entry-vless", "exit-socks"],
  "strip_evasion": true,
  "strip": {
    "xhttp.padding": true,
    "multiplex.padding": false
  },
  "interrupt_exist_connections": false
}
```

## `bridge`

Мостовой аутбаунд для привязки трафика к сетевому мосту Linux и правилам маршрутизации `iproute2`.

> **Статус поддержки:** тип `bridge` и его поля полностью проверяются валидатором конфигурации (`tachyon-core check`), но в текущем runtime v0.6.2 не реализованы — попытка запуска конфигурации с `bridge` вернёт ошибку инициализации.

### Поддерживаемые поля (валидация схемы)

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `type` | `string` | — | Обязательно: `"bridge"`. |
| `tag` | `string` | `""` | Уникальный тег аутбаунда. |
| `interface` | `string` | `""` | Имя сетевого интерфейса. |
| `bridge_name` | `string` | `""` | Имя сетевого моста (bridge). |
| `iproute2_table_index` | `integer` | `0` | Номер таблицы маршрутизации `iproute2`. |
| `iproute2_rule_index` | `integer` | `0` | Приоритет правила `iproute2`. |

Поля `dialer` для `bridge` не поддерживаются.
